Control paths (deliberately NOT the links under test):
  - bench   : wired, via scripts/bsh -> ip netns exec bench -> ssh root@192.168.1.1
  - tiny    : wired, br0/eth0 192.168.100.145 (NOT wlan0). A bench reflash drops
              tiny's wifi; its control path must not ride on it.

Addressing decisions:
  - syd's bench-side address is STATIC 192.168.1.50/24, outside the bench DHCP
    pool (.100-.249, 12h lease). A lease here can expire or be reassigned
    mid-flash; the control path must not depend on one.
  - Stale addresses removed during setup: 192.168.2.101/24 (syd wired),
    192.168.2.60/24 (tiny wlan0). Both were leftovers from an earlier bench
    topology and were why the wired link first appeared "not cabled" - the cable
    was fine, the L3 addressing was simply on a network nobody served.

tiny wifi notes:
  - wlan0 was NM-"unmanaged" and held by a stray wpa_supplicant (PID 4223,
    /run/wifi-client-wlan0.conf) already pinned to BSSID xx:xx:xx:xx:xx:xx, i.e.
    someone had set this up before. Retired it so NetworkManager owns wlan0.
  - A plain `nmcli dev wifi connect ... bssid <5GHz>` still associated to 2.4 GHz
    (phy0-ap0). Pinning the PROFILE with `802-11-wireless.band a` plus the bssid
    is what actually holds it on 5 GHz.
  - Associated: ch36 (5180 MHz), -7 dBm at the AP, tx 325 Mbit/s VHT-MCS 7
    80 MHz VHT-NSS 1.

=== Restored after the v1.9 routed test (2026-07) ===

The routed segment (lan3 in its own br-wired / 192.168.5.0/24) was built only to
engage ECM for finding #1's load test. It has been undone:

  - lan3 is back in br-lan's port list (lan2 lan3 lan4)
  - network.wired and network.brwired deleted; "wired" removed from firewall
    zone lan
  - syd's 192.168.5.50/24 removed from the wired interface

The bench is once again a single 192.168.1.0/24 segment with syd wired on
192.168.1.50 (static, outside the DHCP pool) and tiny on 5 GHz. scripts/bsh
therefore works with its defaults again; the routed runs needed
BENCH_HOST=192.168.5.1 BENCH_ADDR=192.168.5.50/24 overrides.

Verified after the restore that the v1.9 change is unaffected by a network
restart: pool=4096, extra_pbuf=0, SUnreclaim 38,252 kB.

Worth keeping for anyone repeating the routed test: making lan3 a STANDALONE DSA
port does not work (tag_8021q needs bridged ports - a single-port bridge is
fine), the new network must be added to a firewall zone, and the driving host
must DROP its address on the old subnet or the kernel treats the peer as on-link
and never routes.

=== WAN test rig (added to close the acceleration gap) ===

  syd (netns "bench")              RD03v2 bench                 tiny (RPi)
  enx00e04c125990         wired    lan3 -> eth1 (2.5G CPU)
  192.168.1.50/24         ------>  br-lan 192.168.1.1
                                   [ NAT ]
                                   wan  -> eth0 (1G CPU)  wired  eth0 192.168.77.1/24
                                   .77.141 (DHCP)        <------ dnsmasq + iperf3

tiny setup (all runtime-only, nothing persisted to its config):
  - wlan0 moved to the home SSID with ipv4.route-metric 50 and br0's default
    route demoted to metric 700, so Tailscale keeps a path when eth0 leaves the
    LAN. Proven by holding eth0 down 90 s while running SSH sessions that moved
    200 kB each: 3/3 OK. NOTE tiny's own `tailscale ping` reports FAIL during
    that window because it prefers an IPv6 endpoint via br0; the session
    survives over DERP/wlan0 regardless, so ssh reachability is the signal to
    trust, not tailscale ping.
  - eth0 removed from br0 and addressed 192.168.77.1/24 by hand. NetworkManager
    cannot manage it: /etc/NetworkManager/conf.d/10-unmanage-br0.conf pins both
    br0 and eth0 unmanaged.
  - dnsmasq on eth0 only (bind-interfaces, port=0, range .100-.150) plus
    ip_forward=1 and MASQUERADE out of wlan0.

To restore tiny: pkill the /tmp/dq.conf dnsmasq, `ip addr flush dev eth0`,
`ip link set eth0 master br0`, drop the three iptables rules, and put its wlan0
back on whichever AP it should use.

WHY A WIRED LAN CLIENT IS REQUIRED: a Wi-Fi client cannot drive this test. On a
build without the opt-in WIFI_NSS_DONOR integration, ath11k has no nss_offload
parameter, so a Wi-Fi ingress is a non-NSS netdev and ECM will not build an
accelerable rule - ipv4_create_requests stays 0 no matter how much traffic
flows. That single fact explains every earlier "forwarded traffic" run in this
investigation reading 0.
