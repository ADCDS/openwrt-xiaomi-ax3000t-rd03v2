# What the stock investigation changes for v1.9

v1.9 is unreleased, so these can land before anyone flashes them. Ranked by
**megabytes (or bugs) per unit of risk**, with the exact file to touch.

Baselines: stock = RD03v2 ROM 2.0.28; port = `192.168.100.2` running **v1.8**.
`main` has PR #19 on top of v1.8, so re-measure the port side before trusting an
absolute number — the *stock* side is fixed.

| # | Change | Gain | Risk | File |
|---|---|---|---|---|
| 1 | NSS host pool → stock's 4096 | **~3.4–5.2 MB, MEASURED** | low; but `extra_pbuf` is **write-once per boot** | `build.sh` rc.local block |
| 2 | `vm.min_free_kbytes` → 2048 | ~16 MB `MemAvailable` | **medium — needs load testing** | new `files/.../sysctl.d` |
| 3 | Drop the duplicate `q6_mem_regions` node | 0 MB, removes a boot warning | low | board `.dts` |
| 4 | Revisit `NSS_MEM_PROFILE=MEDIUM` rationale | context for #1 | none (doc) | `tools/integrate-wifi-nss.py` |
| 5 | Consider TX pause alongside RX | throughput | medium | `0002-rd03v2-switch-rx-pause.patch` |
| 6 | Align `nf_conntrack_max` with stock | ~1 MB | low | sysctl |
| 7 | Reclaim `tz_apps@4a400000` | 2 MB | **high — TrustZone** | board `.dts` |
| 8 | Re-measure the QCN6122 RSSI offset (reads ~8 dB hot vs stock) | correctness | low to investigate | ath11k patch `952` |

## 1. NSS host buffer pool — the big one

`n2h_empty_pool_buf_core0` is the number of empty skbs the **host** allocates and
hands to the NSS. They sit in Linux slab permanently, so they are pure
`SUnreclaim`.

```
stock: n2h_empty_pool_buf_core0 = 4096   extra_pbuf_core0 = 802816
port : n2h_empty_pool_buf_core0 = 8704   extra_pbuf_core0 = 0
```

Stock asks Linux for **half** as many buffers and compensates with
`extra_pbuf_core0=802816`, which grows the NSS descriptor pool to 14,884 (ours
is 9,984).

> **MEASURED ON HARDWARE (v1.9 bench).** The prediction below is superseded.
> Writing both knobs on a freshly booted NSS build moved `SUnreclaim` by
> **-5,212 kB**, not the ~9,584 kB predicted — 54% of it. The mechanism works:
> `n2h_pbuf_def_total_count` went 9,984 → **14,884**, stock's exact number, with
> no NSS core restart. So this stays an `rc.local` change; it is the *arithmetic*
> that was wrong.
>
> Driving the knob both ways on one boot confirms causality — the drop is not
> boot settling: `8704→4096` gave −5,212 kB, `4096→8704` gave **+4,316 kB**, and
> `8704→4096` again gave −3,420 kB, each within 10 s. An increase on reversal is
> something settling cannot produce.
>
> Solving for the per-buffer cost across those three gives **760–1,332 B**, not
> 2,304 B. That is about `kmalloc-1024` + `skbuff_head_cache` — the payload lands
> one slab class below what the estimate assumed. The old "97% match" was against
> a stock-vs-port `SUnreclaim` *difference* that also contains ath11k,
> module-count and workload differences; it was never a controlled measurement of
> this knob. See `captures/v19-phase2-results.txt`.
>
> **Correction (v1.9 review).** This section previously said those extra
> descriptors are "paid out of the 8 MiB `nss@40000000` carve-out". **They are
> not.** `nss_n2h_buf_pool_cfg()` allocates them with
> `kzalloc(PAGE_SIZE, GFP_ATOMIC)` + `dma_map_single()` — "Add extra NSS bufs
> from **host** memory" — and `nss_core.h` calls the field
> `buf_sz_allocated /* size of bufs allocated from host */`. So 802,816 bytes is
> ~784 KiB of *extra Linux memory*, not a free transfer into the carve-out. The
> change is still net-positive, but both figures in that sum turned out wrong:
> the hardware measurement above supersedes them (~3.4–5.2 MB, not ~9.6 MB),
> because the per-buffer size was overestimated as well.
>
> Also, `extra_pbuf_core0` is **write-once per boot** (`-EPERM` once
> `buf_sz_allocated` is set) — so "runtime-reversible" was wrong for that knob;
> only `n2h_empty_pool_buf_core0` can be re-tuned. And its allocation loop is
> `GFP_ATOMIC` with a `BUG_ON` on the first failed page, which is a direct
> argument against pairing it with finding #2's `vm.min_free_kbytes` cut.

The arithmetic matches the observed slab gap to 97%, and our own
`CONFIG_SKB_RECYCLE_SIZE=2304` in `nss/config.append` is the same 2304 B per
buffer the estimate assumes:

```
(8704 - 4096) x 2304 B = 10,368 kB
SUnreclaim: port 61,492 - stock 50,836 = 10,656 kB
```

Both knobs are `-rw-r--r--` under `/proc/sys/dev/nss/n2hcfg/` (verified on the
port box), so this belongs in the block `build.sh` already prepends to
`rc.local` — right next to `general/redirect` and the accel modes:

```sh
# Host-side NSS buffer pool. The non-LOW default of 8704 buffers costs ~20 MB of
# unreclaimable slab; stock runs 4096 and buys back descriptors with
# extra_pbuf_core0. Note extra_pbuf is ALSO host memory (~784 kB, kzalloc'd and
# dma-mapped), not the nss@40000000 carve-out, and it is write-once per boot.
# See stock-investigation/notes/Q1-MEMORY.md.
echo 802816 > /proc/sys/dev/nss/n2hcfg/extra_pbuf_core0 2>/dev/null
echo 4096   > /proc/sys/dev/nss/n2hcfg/n2h_empty_pool_buf_core0 2>/dev/null
```

**Verify before shipping**, because writing the sysctl is not proof the memory is
returned — the pool may only shrink as buffers are consumed:

```sh
grep SUnreclaim /proc/meminfo
echo 4096 > /proc/sys/dev/nss/n2hcfg/n2h_empty_pool_buf_core0
sleep 30; grep SUnreclaim /proc/meminfo          # measured: ~3.4-5.2 MB lower
grep -E 'pbuf_def_total|payload_alloc_fails' /sys/kernel/debug/qca-nss-drv/stats/n2h
```

If `SUnreclaim` does not drop, the pool is sized at init only and this has to
move to the build-time profile (see #4) instead. Watch
`n2h_payload_alloc_fails` under load afterwards: stock sat at a constant 99
through 2.35 GB of traffic, so a rising counter means 4096 is too few *for our
workload*, which unlike stock's is routed rather than terminated.

Ordering note: set `extra_pbuf_core0` **first**. The driver does not require it —
the two sysctls take independent paths, and `nss_n2h_set_empty_buf_pool()` never
consults `buf_sz_allocated` — so this is a safety convention, not a hardware
constraint: `extra_pbuf_core0` is the write-once knob, so it should be set while
it can still be set, before anything else can fail and abort the sequence.
(The earlier rationale here, "it reconfigures the NSS DDR heap", was part of the
same carve-out misreading corrected above; the pages are host-allocated.)
Confirm too that the NSS core does not need a restart to honour it — if it does,
this becomes a build-time change, not an rc.local one.

## 2. `vm.min_free_kbytes` — biggest number, most caution

```
stock: vm.min_free_kbytes = 2048    zone low watermark  4,096 kB
port : vm.min_free_kbytes = 16384   zone low watermark 20,480 kB  (+ watermark_scale_factor=10)
```

`MemAvailable` subtracts the low watermark, so **16 MB of our reported shortfall
is this sysctl alone**. Stock sets it explicitly in `/etc/sysctl.conf`; ours is
just the kernel's size-derived default. There is no file in the repo that sets
any `vm.*` today, so this would be a new
`files/target/linux/qualcommax/ipq50xx/base-files/etc/sysctl.d/10-rd03v2-mem.conf`.

**Do not ship this on idle numbers.** `min_free_kbytes` is the reserve that keeps
`GFP_ATOMIC` allocations alive in interrupt context — precisely where ath11k RX
and the NSS n2h path allocate. Cutting 16 MB → 2 MB makes `MemAvailable` look
better and makes atomic-allocation failure under burst more likely. Two further
reasons stock's value does not transfer cleanly:

- **Stock is configured to reboot rather than OOM-kill** (`vm.panic_on_oom=2`,
  `kernel.panic=3`). "Stock survives on a 2 MB reserve" is a claim about a box
  that reboots on failure. Ours OOM-kills `hostapd`/`netifd`. Decide that posture
  separately.
- **Stock's watermark ratios are patched.** Its zone reads min 512 / low 1024 /
  high 2560 pages — 1× / 2× / 5×, not mainline 4.4's 1× / 1.25× / 1.5×. Setting
  only the sysctl on our 6.12 kernel gives min 512 / low 640 / high 768, i.e. a
  *tighter* reclaim band than stock, not the same one. If this is pursued,
  `vm.watermark_scale_factor` is the knob that recovers the band.

A defensible middle: **8192**, keeping ~8 MB of reserve while recovering ~8 MB of
`MemAvailable`, tested under the #18 load with `nr_alloc_fail`/`allocstall` in
`/proc/vmstat` watched. Worth pairing with #1, which is the risk-free half.

## 3. Duplicate `q6_mem_regions` reservation

The port box prints this at boot:

```
OF: reserved mem: 0x4b000000..0x4dffffff (49152 KiB) nomap non-reusable wcss@4b000000
OF: reserved mem: 0x4b000000..0x4dffffff (49152 KiB) nomap non-reusable q6_mem_regions@4b000000
OF: reserved mem: OVERLAP DETECTED!
```

Our board `.dts` declares `q6_mem_regions@4b000000` over the same base and size
as the upstream `wcss@4b000000`. Same range, so nothing is lost today — but it is
a duplicate declaration that prints a scary warning and would silently mask a
real overlap later. Either `/delete-node/` the upstream one or drop ours and
reference `wcss` by phandle. Zero MB, one less boot warning.

## 4. The `NSS_MEM_PROFILE=MEDIUM` rationale is contradicted by stock

`tools/integrate-wifi-nss.py` says:

> The NSS build defaults to MEDIUM; LOW caps accelerated connections at 512 per
> family (1024 total), which is too few for the gateway this build is for.

Stock runs `qca_nss_drv.max_ipv4_conn=512` and `max_ipv6_conn=512` — exactly the
LOW numbers — on a consumer gateway. Ours is 2048/2048. That does not make LOW
automatically right for us (a PPPoE gateway with many clients is not stock's
bench case), but the stated reason for MEDIUM should be re-examined rather than
inherited.

The better outcome is to **decouple the two**: keep MEDIUM's connection table and
take LOW's buffer pool via #1's runtime write. The profile ties them together at
build time; the sysctl does not. If #1's runtime write turns out not to free
memory, then the choice really is MEDIUM-vs-LOW and this becomes a live decision.

Also worth deleting while here: stock ships
`dev.nss.ipv4cfg.ipv4_conn=4096` in `/etc/sysctl.d/qca-nss-drv.conf` and **that
sysctl does not exist at runtime** — only `ipv4_accel_mode` and `ipv4_dscp_map`
are present. If we ever copy that file, the line is dead.

## 5. TX pause, not just RX

`0002-rd03v2-switch-rx-pause.patch` sets `FLOW_CTRL_RX` on MAC2 and explicitly
refuses TX pause. Stock's GMAC flow-control register reads **`0xFFFF0006` on both
GMACs** — RFE *and* TFE set, i.e. symmetric pause, on eth0 as well as eth1.

So PR #19's direction is right and stock goes further. Two separate questions
fall out:

- **TX pause on MAC2.** Our patch returns `-EOPNOTSUPP`; stock enables it. TX
  pause means the router can push back on the switch, which has different
  head-of-line-blocking consequences than RX pause. Needs its own bench run.
- **eth0 as well.** Our patch is scoped to `macid == 2`. Stock enables pause on
  both. eth0 is the WAN conduit in the NSS gateway topology, so this is a
  WAN-side question, not a switch-conduit one.

Note for whoever tests: `ethtool -a` reports `RX: off / TX: off` on **both** boxes
and is simply not reporting the MAC state. Use `devmem 0x39c00018 32` /
`devmem 0x39d00018 32`. Bit 1 = TFE, bit 2 = RFE.

## 6. Conntrack table

```
stock: net.netfilter.nf_conntrack_max = 16384
port : net.netfilter.nf_conntrack_max = 32768
```

Small (the hash table is the fixed part; entries are allocated on demand), but
it is free to align if the NSS connection table is 2048/4096 anyway — a conntrack
table four times larger than anything that can be accelerated only buys slowpath
entries. Low priority, bundle with #2's sysctl file if that lands.

## 7. `tz_apps@4a400000` — 2 MB, high risk

Reserved regions, stock vs port:

| | stock | port |
|---|---:|---:|
| `tz@4ac00000` | 4 MiB | 2 MiB |
| `tz_apps@4a400000` | — | 4 MiB |
| total TrustZone | **4 MiB** | **6 MiB** |

Same QSEE binary on both boards, and stock gets away with 4 MiB in one region and
nothing at `0x4a400000`. Matching stock's layout would return 2 MiB.

**This is the one I would not do for v1.9.** TrustZone memory layout is agreed
with a signed blob; getting it wrong is a hang or a subtle secure-world failure,
and 2 MB is not worth it next to #1's 10 MB and #2's 16 MB. Recorded so it is not
rediscovered.

## 8. The 5 GHz RSSI offset looks 8 dB too large

Measured against stock with the same reference client
([`RSSI-VS-STOCK.md`](RSSI-VS-STOCK.md)): patch `952`'s `+31 dB` IPQ5018 offset
and its `GET_NFCAL_POWER` noise floor both check out, but the **`+24 dB`
QCN6122 offset reads about 8 dB hot** — reproducibly, across two passes.

Do **not** change the constant on this alone. The two APs ran different channel
widths (stock 160 MHz ch48, ours 80 MHz ch149) and that is confounded with the
result — note that the band which *agrees* is the band where both run 20 MHz.
The clean experiment is to flash a v1.9 build onto the **bench** RD03v2 once this
investigation is finished, set it to stock's exact channel and width, and repeat
the reciprocity measurement. Same silicon, same room, no confound.

While in there, resolve whether ath11k's reported TX power is per-chain or total
EIRP. It decides both this comparison and whether our 27 dBm on 2.4 GHz (against
BR's 30 dBm ceiling and stock's 30) is a real 3 dB deficit or just a reporting
convention.

## Non-findings worth writing down

Things v1.9 should *not* chase, because the investigation ruled them out:

- **Carve-outs are not the problem.** Stock reserves 65 MiB, we reserve 66 MiB.
  The `qcn9000_pcie0` (17 MiB) and `dma_pool1` (16 MiB) regions in
  `stock_mp03.3.dts` are **not** reserved at runtime — stock's bootloader
  replaces them with 512 KiB stubs. Anything reasoned from that carved DTS about
  memory needs rechecking against `captures/live.dts`.
- **Wi-Fi DMA rings are already competitive.** Stock 16.67 MiB vs our 18.87 MiB
  for both radios. `kmod-ath11k-smallbuffers` has done its job; the remaining gap
  is slab, not rings. The README's "~38 MB ath11k footprint" should be read
  accordingly.
- **Module memory is not it.** Stock carries 206 modules / 10.05 MiB of vmalloc
  against our 87 / ~6 MiB and still comes out ahead.
- **Stock does not leak under load.** 180 s of sustained 5 GHz RX moved
  `SUnreclaim` by +288 kB (0.6%) and it plateaued. The 10 MB difference is a
  fixed allocation, consistent with #1 being sized once at init — not a leak to
  chase.

## Two corrections for the itinerary

Both now noted in the folder README, but they affect planning:

- **No `CONFIG_SLUB_DEBUG` on stock *or* on our build.** No `/proc/slabinfo`, and
  the SLUB sysfs object counters are absent. Phase 2's "compare caches one by one
  by object count" cannot be run. If per-cache attribution ever matters, we would
  need a debug kernel on **our** side — it is unobtainable on stock.
- **The dmesg ring wraps well inside an hour.** Boot-time lines are gone by the
  time you ssh in. Capture from cold boot or over UART.

## What is still unmeasured

- **The #18 comparison proper.** Needs a wired host on one of the RD03v2's LAN
  ports so traffic is *forwarded* (5 GHz ↔ wired, engaging ECM) rather than
  terminated on the router, and hours rather than minutes. The bench has no wired
  client on the stock unit's LAN today. This is the single highest-value bench
  improvement.
- **Whether #1 actually frees memory at runtime.** One command on a test box.
- **Stock's crash-stop ordering** (phase 7c) — relevant to the 0823/0825 respawn
  patches, not to memory. Stock's `restart_level` is **`RELATED`**, not `SYSTEM`,
  so a Wi-Fi crash resetting the board is a failure there too, not policy.
