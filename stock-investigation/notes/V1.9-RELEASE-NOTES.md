## v1.9 — ~6 MB of RAM back, and a boot warning gone

This release is the first one informed by a **live inspection of stock firmware**.
A stock RD03v2 (ROM 2.0.28) was rooted and measured on the bench, and the
comparison is in [`stock-investigation/`](stock-investigation/) — captures,
scripts and analysis. Three of its findings land here; the rest are recorded with
the reasons they were deferred.

### Memory: ~6 MB returned

Stock hands the NSS **4096** host-side buffers where the NSS memory profile
defaults to 8704. Those are empty skbs pinned in Linux slab as `SUnreclaim` — pure
unreclaimable overhead on a box that only sees 175 MB. v1.9 matches stock's value
from a new `/etc/init.d/nss-bufpool`.

Measured on matched idle boots of the same image, differing only in whether the
script ran:

| | without | with |
|---|---:|---:|
| `SUnreclaim` | 44,576 kB | 38,204 / 38,144 kB |
| `MemAvailable` | 37,088 kB | ~42,800 kB |

That is roughly **15% more `MemAvailable`** on a device whose documented failure
mode is the OOM killer shooting `hostapd`. Compare at idle; `SUnreclaim` drifts
about 1 MB once clients associate.

It affects NSS builds only in practice — on a plain build the sysctl tree does not
exist and the script is a no-op. Revert at runtime with
`/etc/init.d/nss-bufpool stop`; nothing else changes.

**What this deliberately does *not* do.** Stock also sets
`extra_pbuf_core0=802816`. v1.9 does not, because that knob *costs* ~784 kB of
host memory rather than saving any (despite the name it is `kzalloc(GFP_ATOMIC)`
pages, not the `nss@40000000` carve-out), it is write-once per boot, and its
allocator calls `BUG_ON` on a failed page across each of seven messages — which on
this board (`panic_on_oops=1`, `kernel.panic=3`) would be a boot reboot loop, not
a warning. Dropping it also turned out to *gain* about 0.8 MB rather than cost it.
Descriptor count is unchanged from v1.8 either way (9,984).

### A boot-time warning fixed

The board device tree declared its own Q6 `reserved-memory` node over the same
range as the upstream one, so every boot printed:

```
OF: reserved mem: OVERLAP DETECTED!
wcss@4b000000 ... overlaps with q6_mem_regions@4b000000
```

Nothing was lost — both claimed the same 48 MiB — but a duplicate that trips the
overlap detector would also mask a genuine overlap later. The node was redundant
in full and is gone; the carve-out is byte-identical, verified by diffing the
decompiled DTBs and confirmed on hardware.

### Documentation corrected

The rationale for `NSS_MEM_PROFILE=MEDIUM` claimed LOW's 512-connections-per-family
cap was "too few for the gateway this build is for". Stock runs exactly those 512
on a consumer gateway, so the stated reason was wrong even though the choice
stands. Corrected, along with a memory-provenance error that had propagated
through the investigation notes.

## NSS Wi-Fi offload is now in the `-nss` images

Until now the `-nss` images offloaded only the **wired** data plane. Every Wi-Fi
packet still went through the CPU, and ECM could not accelerate a flow with a
Wi-Fi end at all — which is why 5 GHz↔WAN throughput lagged so far behind wired
NAT. The `-nss` images now include the NSS Wi-Fi integration, so those flows can
be accelerated too.

This is the newest and least-exercised part of the port. It is built from a
pinned external donor tree, and `docs/nss-wifi-validation.md` records exactly
what was tested and what was not — notably, no WAN benchmark. If you hit Wi-Fi
trouble, the plain image does not include any of this.

## Upgrading — please read

**`/etc/rc.local` survives every upgrade.** It is in
`/lib/upgrade/keep.d/base-files-essential` and `sysupgrade` saves config by
default, so a plain `sysupgrade <image>` — no flags — restores *your* `rc.local`
over the new image's. On an NSS build that file carries the offload knobs
(`general/redirect`, the accel modes), so an NSS → NSS upgrade keeps whatever you
already had and any change to that block silently does not apply. After upgrading:

```sh
cmp -s /etc/rc.local /rom/etc/rc.local || cp /rom/etc/rc.local /etc/rc.local
reboot          # then: cat /proc/sys/dev/nss/general/redirect   -> 1
```

This is exactly why v1.9's pool setting is in `/etc/init.d/nss-bufpool` and not in
`rc.local`: `/etc/init.d` is in no keep list, so the image's copy always wins.

**Flashing is unchanged** — pivot into the initramfs and run `sysupgrade` from
there, per [`docs/no-uart-reflash.md`](docs/no-uart-reflash.md). In-place
`sysupgrade` is refused by the platform.

## Known gaps

- **Many-client behaviour under acceleration is unmeasured.** The buffer-pool
  change *was* tested under a genuinely accelerated WAN↔LAN NAT flow (see
  below), but with one TCP flow plus a bidirectional pair — not dozens of
  clients with bursty small packets. Stock ships the same 4096 on identical
  silicon as a consumer gateway, which is the best evidence for that case.
  Watch `n2h_payload_alloc_fails` on a heavy multi-client workload and report a
  rising counter.
- **Three kmods are absent from the tarball**: `qca-mcs`, `qca-nss-crypto` and
  `dahdi-linux` fail to build against this kernel. None is in either image.

## Verified under load

The pool change was tested with the NSS fast path genuinely engaged — a
dual-CPU-port gateway topology (LAN on `eth1`, WAN on `eth0`), wired client
through NAT to an upstream server:

| | pool = 4096 (v1.9) | pool = 8704 (old default) |
|---|---:|---:|
| Throughput | 940 Mbit/s | 939 Mbit/s |
| `n2h_payload_alloc_fails` | unchanged | unchanged |
| `SUnreclaim` | 42,304 kB | 48,812 kB |

`ipv4_create_requests` climbed 0 → 5, confirming acceleration was real rather
than the exception path. ~9 GB of accelerated NAT traffic produced **zero**
allocation failures. The larger pool bought 1 Mbit/s — noise — and cost 6.4 MB.

The released images themselves were then flash-tested end to end: the
`initramfs-factory-nss.ubi` from this asset set was written and read back
(byte-exact), booted from RAM, and used to `sysupgrade` the release
`sysupgrade-nss.bin`. From NAND the box logs `nss-bufpool: pool 8704 -> 4096`
at boot with `pool=4096`, `dmesg` reports no `OVERLAP DETECTED`, and both radios
come up — so both findings are confirmed in the shipped binary, not just in the
source tree.

## Deferred, with reasons

Recorded in [`stock-investigation/notes/V1.9-TUNING.md`](stock-investigation/notes/V1.9-TUNING.md):

- **`vm.min_free_kbytes` 16384 → 2048** (~16 MB of reported `MemAvailable`). Not
  shipped: that reserve is what keeps `GFP_ATOMIC` allocations alive in interrupt
  context, exactly where ath11k RX and the NSS n2h path allocate. Stock survives
  on 2 MB partly because it is configured to *reboot* rather than OOM-kill. Needs
  load testing, and must **not** be combined with anything that allocates
  atomically at boot.
- **TX pause alongside RX** — stock runs symmetric pause on both GMACs; ours is
  RX-only on the switch conduit. Needs its own bench run.
- **`tz_apps@4a400000`** (2 MiB) — TrustZone layout, agreed with a signed blob.
  Not worth it.
- **The 5 GHz RSSI offset** reads ~8 dB hot against stock, but the comparison is
  confounded by different channel widths. Needs a controlled re-measurement.
